# CPU Worker Top K：实现与验证（2026-10-04）

CPU Worker 已改为批内保留前 K 名，只返回索引和分数，主线程合并后重建最终 K 行。旧的 46.2 MB 结果缓冲及其清零、回收逻辑已从 CPU 调度路径移除。**资源开销明显减少，总耗时收益有限**：本轮百万组合 K=1024 的热运行均值减少约 8.3%，K=10 增加约 3.5%，真实默认任务基本持平。保留改动，但不宣称普遍提速。

这是[GPU 溢出分块](gpu-overflow-performance.md)、[GPU 按目标裁剪](gpu-objective-performance.md)之后的第三阶段。详细输入、旧源码、两份隔离构建、逐行结果和日志保存在 Git 忽略的 `output/performance-cpu-topk-20261004/`。

## 实现和取舍

原路径为每个通过筛选的组合打包 77 个 float32 数值。每个任务从主线程接收固定 `150000 × 77 × 4 = 46,200,000` 字节的缓冲，返回后主线程逐行解包、建立对象、筛选 Top K，再清零复用。

现在每个 Worker 使用数值最小堆保留至多 K 项，输出交错排列的 Float64 索引／分数对，每项 16 字节。主线程同样用数值堆合并，最终通过 `simulateBuild` 和原有行打包格式重建 K 行。返回数据长度明确，空结果不再依赖 HP 非零哨兵。

- `optimizerWorker.ts`：移除热循环中的完整行打包，加入批内 Top K 和局部门槛。
- `cpuResultScore.ts`：统一基础／战斗属性、CR/CD boost、忆灵变换、EHP、技能和全局评分读取；保持原 CPU float32 排序精度。
- `cpuResultRows.ts`：仅重建最终候选，保留原 CPU 行精度；全局索引直接赋值，避免经过 float32 或 32 位整数截断。
- `optimizer.ts`：合并紧凑结果，删除大缓冲池及相关重试回收分支。Worker 调度、批次大小和线程池重试机制保持原有结构。

每批未进入前 K 名的候选，在同一批已有至少 K 个分数不低于它的候选，因此不会影响全局前 K 名的分数集合。同分候选的具体身份可以不同；结果仍须唯一。局部和全局门槛只在堆满后提高，初始为负无穷，支持零分和负分。

新增的最终 K 次模拟有成本，批内堆也需要比较操作。这次没有裁剪 CPU 技能计算、缓存整份 Worker 上下文或改变评分公式，不能把返回数据减少比例当作总耗时减少比例。

## 性能结果

固定顺序为 **旧 1 → 新 1 → 新 2 → 旧 2**。每组每场景运行三次，分别为独立浏览器中的首次运行，以及两次同浏览器内的重复运行。每版本每场景首次 n=2、热运行 n=4，总计 **36/36 次完成**，没有超时或替换输入。

环境为 Windows、Intel i5-12500H、16 个逻辑 CPU、Node 26.10.0、隔离 Edge 浏览器。CPU 线程池上限为 10。两版安装相同的 Worker 消息字节计数器；计时从提交到观察到完成，页面内每 10 ms 轮询，结果验证在计时之外。测试、构建与测量串行执行，未隔离系统后台负载，也未锁定处理器频率。

| 场景                             | 旧版首次均值 | 新版首次均值 | 旧版热运行均值 | 新版热运行均值 | 热运行耗时变化 |
| -------------------------------- | -----------: | -----------: | -------------: | -------------: | -------------- |
| 合成百万组合，K=10               |      2.490 s |      2.484 s |        2.040 s |        2.111 s | +71 ms，+3.5%  |
| 合成百万组合，K=1024             |      2.603 s |      2.720 s |        2.156 s |        1.977 s | −178 ms，−8.3% |

首次 K=1024 的两种场景分别慢约 117 ms、582 ms。两版后半段运行整体更快，波动不小：百万组合 K=10 热运行旧版范围 1.611–2.566 s、新版 1.752–2.463 s；K=1024 旧版 1.628–2.653 s、新版 1.662–2.368 s；真实任务旧版 9.160–11.194 s、新版 9.605–10.878 s。以上均值是描述性结果，不足以推断稳定尾延迟或全设备加速。

前两个场景来自仓库镜流样本，每槽扩展为 10 件带独立 ID 和可复现属性差异的遗器；它们是受控合成输入。第三个场景使用本地真实库存的 `8004` 原始默认配置，排序为 `TALENT_SHIELD`，没有缩减库存或修改默认筛选。它只覆盖一个真实角色任务，不是全账号完成度验证。

旧版还将等量的空结果缓冲从主线程传给 Worker；新版这部分为 0。上下文和遗器输入仍通过 structured clone 发送，未计入此表，也未声称消除了这些数据传输。

单条结果消息由固定 46.2 MB 变为至多 160 B（K=10）或 16 KiB（K=1024）。这些是跨线程传递的 ArrayBuffer 容量，transfer 会转移所有权；累计数不等于物理复制量、网络流量、应用 RSS 或峰值内存。本轮未测全进程常驻内存，不能把旧缓冲池容量直接当作实测内存降幅。

## 正确性与原版对照

按用户建议，保留并使用改动前的 Worker 逻辑。端到端性能的旧版使用未作本轮修改的隔离构建；它包含此前已有的自动化和 GPU 工作，不是干净上游应用的整体基线。

逐批对照还发现两个既有门槛行为：旧版战斗基础属性排序没有应用对应的计算后门槛；EHP 等计算评分则用未舍入值比较来自 float32 行的门槛，可能丢弃按最终分数应保留的同分候选。因此，最终逐批数值参考使用原 Worker 关闭旧门槛后的完整打包结果，再按实际 float32 分数筛选。首次直接比较的差异日志保留，未把调整后的对照称为原门槛行为完全一致。

新路径为门槛和堆排序统一使用 float32 分数。显式测试覆盖 `1 - 2^-26` 在 float32 中舍入为 1 后仍通过门槛 1，以及初始负分、零分同分、不足 K、空结果、乱序批次、短尾和超过 `2^32` 的索引。

- **24,696 个候选**逐项独立模拟，适用数值字段的最大相对误差约 **5.90e-8**，均低于 `1e-5`。
- 每场景其余 11 次运行与一次旧版参考比较，**22,638 对排序分数完全相同**，最大误差 0。
- 每次结果数量和组合唯一性通过；校验六部位、主属性、强化、星级和优先级占用限制。
- **45 项仓库定向单元测试 + 19 项本地旧版参考检查，共 64 项通过**。其中新 Worker 测试以独立六重循环穷举 64 组合，比较分批合并后的前 K 名及重建行。
- **11 项 CPU 目标、11 项 GPU 目标、10 项已有自动化浏览器检查通过**，包含技能／EHP 筛选、忆灵、取消、失败和 tuple 回归。通过结果来自两次运行：初次组合运行的 10 项通用和 11 项 GPU 通过；修正字段适用范围后，CPU 11 项单独通过。

无忆灵角色的旧 CPU 行包含零值忆灵占位字段，其中 `mELEMENTAL_DMG` 与独立模拟的填充值不同；这类不适用字段不计入重算比较。有忆灵角色的字段仍逐项验证。搜索编号和库存权重也不属于独立模拟数值口径。

为了让合法的全局排序目标可被完整展示和核对，CPU 最终行及公共模拟格式补出 `COMBO_HEAL`、`COMBO_SHIELD`、`COMBO_BUFF` 三个已有寄存器的数值。没有改变其计算公式。浏览器组合评分用例包含零分同分场景，不代表所有治疗／护盾／增益角色机制的完整验证。

独立只读审查未发现严重或重要问题。快速类型检查、自动化类型检查、生产构建和两份基准构建均退出 0；Lint 为 0 警告、0 错误。真实大任务的旧版对照和候选重算，不等于整个空间的独立最优性穷举证明。
