# Node 模拟性能基线

后续浏览器 CPU/GPU、库存、批量、评分和 MCP 的测量见 [全链路性能基线](performance-baseline.md)。本文保留早先 Node 专项结果，以下“未测浏览器”描述仅限当时这一轮。

2026-10-03 本机测量：当前实现的主要交互成本是新建进程和初始化；预热后的单次模拟已接近毫秒级。优先评估复用进程和减少重复准备工作，再决定哪些热点值得迁移 Rust。没有测量浏览器性能，不能据此声称比浏览器快多少。

以下首轮基线保留用于历史对照；同日实施的索引优化及交替 A/B 结果见文末“索引优化”。

## 结果

环境：Windows x64、Node v26.10.0、Intel i5-12500H、16 个逻辑 CPU、约 15.7 GiB 物理内存。基准串行执行，没有同时运行测试或构建，但未隔离系统后台负载。

输入为仓库 `src/data/sample-save.json`（247449 字节、162 件遗器）。角色为 `1212b1`、`1005`、`1102`、`1217`、`1205`。每次比较包含基线及 4 个候选：替换技能序列、预测主属性升级、替换队友、重复基线，共 5 次模拟。重复基线也实际计算，不缓存结果。

| 指标                       |     单次模拟 |               比较 5 套配装 |
| -------------------------- | -----------: | --------------------------: |
| 新进程端到端中位数         |    296.79 ms |                   308.54 ms |
| 新进程端到端 P95           |    366.64 ms |                   351.12 ms |
| CLI 执行部分中位数         |     70.53 ms |                    80.30 ms |
| 新进程峰值 RSS 中位数      |   119.12 MiB |                  119.27 MiB |
| 预热后每请求均摊时间中位数 |     0.849 ms |                    4.069 ms |
| 预热后每请求均摊时间 P95   |     1.425 ms |                    6.487 ms |
| 预热后吞吐量               | 1078 请求/秒 | 230 比较/秒（1151 模拟/秒） |

连续计算的 5 个进程，峰值 RSS 中位数为 **196.29 MiB**，范围 **192.41–238.41 MiB**。这是工作集高水位，不是私有内存或 JavaScript 堆大小，也不是内存泄漏结论。未强制 GC、未设置堆大小限制，不能把预热吞吐量理解为不增加内存即可获得的加速。

## 测量口径

- 每种命令启动 30 个新进程，5 个角色各重复 6 次。端到端时间包含进程启动、模块加载、输入读取、存档处理、计算、JSON 输出和退出。系统文件缓存未清空，所以这是进程冷启动，不是磁盘冷启动。
- 峰值由轻量预加载脚本在退出时读取 `process.resourceUsage().maxRSS`，这个脚本的加载也包含在端到端时间中。
- CLI 执行部分不含模块加载，仍包含存档准备和输出，不能视为纯计算时间。
- 预热实验使用 5 个独立进程；每种命令预热 20 轮，再测 100 轮，每轮依次计算 5 个角色。表中的延迟是每轮总时间除以 5 的分布，**不是单请求尾延迟**。总计测量 2500 次单独模拟和 2500 次比较，即 15000 次模拟，不计预热。
- 预热计时不包含初始化、请求 Schema 校验和输出序列化，但保留实际核心的请求归一化、克隆、上下文构建、计算和比较结果生成。它是基准脚本，当前正式 CLI 仍每次新建进程。
- 冷启动输出按角色/命令验证哈希一致；预热结束后验证输出与初始结果深度相等。没有改动生产计算实现。

## 索引优化（2026-10-03）

移除 `ComputedStatsContainerConfig.actionBuffIndices`。它原来为每个目标标签和每个属性生成完整地址数组，而已有的 `entityBaseOffsets` 保存了相同目标的实体基础地址。`actionBuff` / `actionSet` 现在用基础地址加属性索引，保留单实体快速路径及多实体写入顺序。

这一改动取消了按属性重复分配数组的步骤：准备工作的目标匹配从 `O(目标标签 × 属性 × 实体)` 降为已有的 `O(目标标签 × 实体)`，每次属性写入仍为 `O(匹配实体)`。没有引入全局缓存，也没有删除防止候选相互污染的深拷贝。

### 交替 A/B 性能

使用冻结的旧版、新版 worker，以 AB、BA、AB、BA 顺序串行运行 4 轮，每版每种负载 4 个独立进程。每进程仍按首轮基准预热 20 轮、测量 100 轮；报告值为各进程“总计时 / 请求数”的中位数，与前文“每轮均摊时间”的统计口径不同。

| 负载                   |    优化前 |   优化后 | 耗时下降 |
| ---------------------- | --------: | -------: | -------: |
| 原样本：单次模拟       |  0.902 ms | 0.638 ms |    29.3% |
| 原样本：比较 5 套      |  3.864 ms | 2.666 ms |    31.0% |
| 召唤物/忆灵：单次模拟  |  1.938 ms | 0.933 ms |    51.9% |
| 召唤物/忆灵：比较 5 套 | 10.075 ms | 4.315 ms |    57.2% |

原样本峰值 RSS 中位数从 190.03 降到 185.38 MiB；召唤物/忆灵负载从 219.54 降到 191.22 MiB。后者使用景元、阿格莱雅、遐蝶、风堇、记忆开拓者（`1204/1402/1407/1409/8007`），固定遗器、默认配置与同命途光锥，比较星魂、技能序列和击破状态。它是计算负载，不是这些角色的推荐配装。

各轮配对的平均耗时均改善，但系统未隔离后台负载，召唤物负载旧版的波动较大。以上是样本内结果，不是所有角色、库存规模或 CPU/GPU 搜索的加速保证。新进程端到端成本仍主要在启动和初始化，预热收益不能直接换算为 CLI 总耗时收益。

### 等价性证据

- 先在旧版运行新增目标写入测试，再在新版运行：覆盖 10 个目标标签、8 种实体布局、2 种忆灵优先设置、3 种命中数量和序列化前后，共 96 个配置。逐一写入所有行动属性，对比完整数组，包括命中与寄存器区域；覆盖负零、极端有限值、无穷和 NaN。
- 使用两份冻结构建产物对照当前数据中的全部 108 个角色配置。每个角色比较默认、满星魂、技能序列、满星魂加击破、队友配置，合计 **540 组模拟完整输出完全一致**；108/108 请求成功，没有排除错误样本。这没有穷尽所有技能条件、套装和队伍组合。
- 原样本冷启动的 10 种角色/命令输出哈希与优化前一致。
- 最终回归：112 个单元测试文件通过，1201 项通过、3 项跳过；20 项网页/Node/MCP 自动化全部通过，包含真实 CPU/GPU 搜索及结果对照。应用及自动化类型检查、lint、生产构建和差异格式检查通过。独立代码审查未发现本次修改的正确性问题。
