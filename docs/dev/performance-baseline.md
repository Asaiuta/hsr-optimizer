# 全链路性能基线（2026-10-03）

后续 GPU 溢出分块的实现、真实库存对照及跨显卡性能取舍见 [GPU 溢出分块验证](gpu-overflow-performance.md)。

后续阶段还包括 [GPU 按目标裁剪](gpu-objective-performance.md)、[CPU Worker Top K](cpu-topk-performance.md)和 [CPU 按目标裁剪](cpu-objective-performance.md)，各自保留独立对照和性能边界。

千亿、万亿任务的计数口径、验证缺口与修正后的优化顺序见[真实库存的大规模搜索口径](large-search-scale.md)；本文的小任务启动开销结论不能直接决定大规模搜索的优先级。

本轮已覆盖浏览器 CPU/GPU 搜索、Node 计算阶段、库存读写、批量任务、评分、分配及 MCP 调用。当前最明确的热点是 GPU 溢出重跑和首次管线编译；其次是 CPU 结果处理、固定套装枚举和上下文复制。这里只建立基线，没有修改生产算法，也没有新增 Rust 引擎。

另发现一个独立的可靠性问题：**导入 10000 件遗器返回成功，但持久化内容仍为之前的 5000 件**。这项时间不能作为成功保存的成绩。存储配额是疑点，原始异常未被本轮生产构建记录，不能把推断当作已捕获的错误类型。

## 环境与口径

- Windows x64，Intel i5-12500H，16 个逻辑 CPU，约 15.7 GiB 内存；Node v26.10.0；Playwright 启动隔离的 Edge 无头实例。
- WebGPU 实际适配器为 `intel / gen-12lp`。适配器支持 timestamp query，但本轮未采集 GPU 内核时间戳或真实显存占用。
- 分支 `feat/ai-automation`，基准提交 `bd427fa36e056a905d53d0338e518c146501ea9c`，包含本地未提交修改。提交号不能单独还原本次实现；结束时文件哈希见产物清单。
- 搜索用仓库 `src/data/sample-save.json` 中的 `1212b1`，按六个槽位扩展为带独立 ID 和小幅属性变化的合成遗器。规模测试不代表真实大账号的套装、属性和角色多样性。
- 测量串行运行，没有同时执行构建或测试；系统后台负载未隔离。三次顺序样本分别呈现，不据此估计 P95 或稳定尾延迟。
- `browser-report.json` 使用生产构建，但始终安装 Worker/GPU API 探针。`diagnostic-*` 另外使用独立插桩构建。两者都不是完全无探针基线。
- 搜索端到端包含请求、准备、计算、结果处理及完成状态轮询（页面内每 10 ms）。诊断阶段包含嵌套调用，不能相加得到总时间；Worker 的计算时间彼此重叠，也不能相加视为墙钟时间。
- `mapAsync` 包含 GPU 排队、执行及回读等待，不能等同于 GPU 内核耗时。GPU buffer 数字仅为显式申请/销毁统计，不包含驱动分配。
- 所有数据写入测试浏览器的隔离存储，没有使用用户的浏览器配置或游戏账号。

### 已定位阶段

| 测量点                       | 观测                                        | 解释与后续方向                                             |
| ---------------------------- | ------------------------------------------- | ---------------------------------------------------------- |

| 百万组合 GPU 溢出重跑        | 后两次 2273.2 / 2073.0 ms                   | 已占主要等待；优先审查溢出策略和结果筛选                   |
| 299 万组合 GPU 溢出重跑      | 后两次 5917.9 / 5821.9 ms                   | 末次整个 naive dispatch 为 6401.1 ms；重跑为其中的嵌套阶段 |
| 套装组合生成                 | 约 33–35 ms                                 | 小任务也有可见固定成本，需评估减少重复枚举                 |
| 百万组合 CPU Worker 同步发送 | 总计约 11.5–15.8 ms                         | 为主线程发送 API 耗时，不是完整传输/计算延迟               |
| 299 万组合 CPU 结果解包      | 末次 24 次调用合计 281.7 ms                 | 主线程结果处理值得进一步剖析                               |
| 同组缓冲区清理               | 24 次合计 85.8 ms                           | 与解包分开观测；不要直接当作可消除时间                     |
| 百万组合末次 GPU 输出重算    | 0.6 ms                                      | 当前 10 个结果的重算不是该任务主要瓶颈                     |

诊断数据还覆盖四件套约束：36 件遗器、2916 个有效组合。CPU 87.0 ms；GPU 首次 3112.8 ms，其中编译 2595.8 ms、`runTupleDispatch` 248.7 ms。这说明 tuple 路径已实际执行，但仅测了一个冷任务，没有代表性的稳态 tuple 分布。

附加任务覆盖结果上限 1/100 和无结果约束，各引擎各一次；其值保留在原始报告中，不用于推断稳定延迟。299 万组合 CPU 末次的 24 个批次共通过 1079554 个候选，覆盖了后续批次动态提高筛选阈值的情况。

### 正确性核对边界

- 正常规模任务均核对组合数量、完成状态和 10 项结果，并逐项重新模拟，要求 COMBO 相对误差小于 `1e-5`。
- 对生产矩阵、诊断矩阵及大规模矩阵共 **27 对 CPU/GPU 任务、270 对排序后分数**做离线核对，最大相对误差约 `3.62e-8`，全部满足相同误差门限，详见 `cross-engine-check.json`。相同分数不要求遗器 ID 或并列顺序相同。
- 这验证了本批返回结果的一致性，不是独立穷举 oracle，不能证明全局 top-K 完整性或所有角色机制零回归。

## 保存可靠性、内存和 MCP

独立集成运行实际读取 `localStorage` 校验，而非只检查 API 成功字段：

| 请求导入 | 实际持久化数量 | 存储 JSON UTF-8 字节 | 一致   |
| -------- | -------------: | -------------------: | ------ |
| 1000     |           1000 |               600226 | 是     |
| 5000     |           5000 |              2970489 | 是     |
| 10000    |           5000 |              2970489 | **否** |

`SaveState.save()` 捕获 `localStorage.setItem` 异常后仍返回序列化字符串，自动化调用未据此报告保存失败。大存档触发配额限制与观测相符，但本轮没有保留原始异常。下一步应先让保存失败可观测，再评估存储方案；本轮没有顺带修改此行为。

恢复样例存档后连续三轮、每轮 2000 次模拟，耗时 1181.7 / 1130.9 / 1105.8 ms。每轮强制 GC 后主渲染进程保留堆分别 **29814516 / 29836660 / 29826748 字节（约 28.4 MiB）**，这段 6000 次调用未显示持续增长。强制 GC 是诊断手段，不能据此证明长时间无泄漏；Worker、GPU、浏览器进程也不包含在此堆指标内。

OS 工作集、峰值和私有内存以每进程记录在 `integration-report.json`，保留角色/PID 对照。共享工作集不能简单相加。浏览器生产探针运行的 5 s 空闲窗口，主线程 TaskDuration 增加约 11.5 ms；未测多小时空闲功耗。

隔离样例还执行了 10 轮方案保存、冲突检查、换装和删除。MCP 以 stdio 直接连接本地桥接，连接 568.6 ms，首次工具发现 939.7 ms（包含浏览器启动/加载），共 31 个工具；文件导入 34.0 ms，扫描器状态读取 2.41 ms，首次模拟 10.96 ms，随后约 3.8–5.0 ms，返回约 1912 字节。**这不等于已在 Codex 中注册 MCP**。没有启动扫描、触发 UAC 或操作游戏。

## 重现与产物

在仓库根目录使用 Node 26+、已有项目依赖及本机 Edge；保证 4175 端口空闲。命令依次执行，每一步成功后再运行下一步，不要让不同基准同时争用 CPU/GPU。重跑会覆盖对应输出，应先归档需要保留的结果。

```powershell
npm run build
node scripts/benchmark-browser.mts
node scripts/benchmark-core.mts
node scripts/benchmark-scoring.mts
node scripts/benchmark-integration.mts
node scripts/benchmark-instrument.mts
node scripts/benchmark-browser.mts --diagnostic
node scripts/benchmark-browser.mts --diagnostic --large-search
```

主要产物位于仓库 `output/performance-suite/`（本地输出，不纳入生产构建）：

- `browser-report.json`：生产构建加 API 探针的规模矩阵和工作流。
- `diagnostic-browser-report.json`：修正异步计时后的阶段报告；`diagnostic-browser-first.json` 是被替代的早期诊断，不用于结论。
- `large-diagnostic-browser-report.json`：新增缓冲区探针后的大规模测量。早先诊断报告使用的构建与该次不同，不应视为同一二进制。
- `core-report.json`、`scoring-report.json`、`integration-report.json`：各独立测量的样本及说明。
- `cross-engine-check.json`：本轮离线比对的 27 对任务及误差。
- `current-renderer.cpuprofile`：独立采样运行，名称被压缩，仅作辅助定位，不混入计时结论。
- `manifest.json`：结束时源码/脚本、当前构建和报告 SHA-256 快照；这是收尾快照，不冒充早先构建的完整追溯记录。

先前 Node 启动/吞吐测量和索引优化 A/B 保留在 [Node 模拟性能基线](headless-performance.md)，与本轮范围分开。

真实账号测量使用 `scripts/benchmark-real-core.mts SAVE.json OUTPUT_DIRECTORY` 与 `scripts/benchmark-real.mts SAVE.json OUTPUT_DIRECTORY`，串行运行。前者测 Node 核心与评分，后者用真实库存测浏览器、搜索、内存和 MCP。当前代表性搜索角色 ID 固定在脚本中，需按账号调整；采用当前四件套/二件套和主属性，缺少配装或引擎不接受的配置会明确跳过。原始账号数据和详细结果保存在本地 `output/`，不要提交到仓库。

若要测量原版默认配置，依次运行 `node scripts/benchmark-default-plan.mts SAVE.json OUTPUT_DIRECTORY`、`node scripts/benchmark-default-build.mts OUTPUT_DIRECTORY` 和 `node scripts/benchmark-default.mts OUTPUT_DIRECTORY`。规划阶段恢复角色默认表单，保留扫描身份、装备和库存顺序；使用 GPU Stable、至少 +9 的 5 星遗器、推荐主属性、无套装限制和 1024 项结果。独立测量构建添加启动入口以绕过公开 API 的 100 项结果上限，不改变生产接口或算法。默认代表角色针对本地账号；也可传入 `OUTPUT_DIRECTORY ID1,ID2 600 1` 指定角色、每次观察秒数及重复次数。限时取消必须报告为未完成，UI 100% 也不能代替任务完成状态。该流程测量当前引擎在原版配置下的行为，不构成与未修改上游引擎的 A/B 对比。

本轮验证：生产/诊断/大规模共 68 个搜索任务完成，三个报告的错误数组及页面错误数组均为空；集成脚本完成 10 轮方案操作和 22 次 MCP 工具调用。自动化 TypeScript 检查、lint（0 警告、0 错误）及 `git diff --check` 通过。没有修改生产算法，因此未重复执行整套应用功能回归；这些检查也不替代未来算法修改后的正确性验收。
